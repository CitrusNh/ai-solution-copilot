# 系统架构与实现说明

## 一句话

系统把“客户问题”转换成检索请求，从产品资料中找出带来源的证据，再由本地规则生成售前分析卡；遇到 BYOK、等保、数据驻留等资料未承诺的需求时，明确升级人工确认。

## 用户可见流程

```text
上传 MD/TXT/PDF
        ↓
解析与切分（保留文件名、章节/页码）
        ↓
字符级 TF-IDF + 业务意图加权检索
        ↓
句子级相关性过滤与风险识别
        ↓
售前分析卡
  ├─ 客户需求摘要
  ├─ 匹配能力
  ├─ 限制与风险
  ├─ 继续询问客户的问题
  └─ 带来源的回复草稿
        ↓
Markdown 报告下载 + 本地反馈记录
```

## 模块职责

| 模块 | 作用 | 面试时要点 |
|---|---|---|
| `app.py` | Streamlit 页面、上传、检索、分析卡、下载和反馈入口 | 页面是产品流程的可运行载体 |
| `src/ingest.py` | 解析 MD/TXT/PDF，限制 10MB，保留来源元数据 | 先处理可追溯性和输入边界 |
| `src/retrieve.py` | 文档切分、字符级 TF-IDF、业务意图加权 | 中文无分词依赖，结果可解释 |
| `src/solution_card.py` | 句子相关性过滤、风险阻断、回复草稿 | 检索命中不等于可以直接承诺 |
| `src/reporting.py` | Markdown 报告和本地反馈 CSV | 让结果可带走、可复核、可迭代 |
| `src/embeddings.py` | 可选 OpenAI 兼容 Embedding 客户端、缓存和预算保护 | 作为后续实验，不是 MVP 运行前置条件 |
| `src/semantic_retrieve.py` | 语义/混合检索实验 | 用同一评测集比较，而不是为了“上模型”而上模型 |

## 当前数据边界

- 这不是生产系统，而是用于求职展示和产品验证的可运行 MVP。
- 演示资料位于 `data/demo/`，是虚构的产品说明、价格限制和安全 FAQ。
- 上传文件只在当前 Streamlit 会话中解析，不写入 Git。
- 本地反馈写入 `data/feedback/`，Embedding 缓存写入 `data/cache/`；两者均在 `.gitignore` 中。
- 当前规则版本不调用聊天模型，API 成本为 0；Embedding 仅在用户明确配置兼容接口并运行实验时调用。

## 关键产品决策

### 为什么先做本地规则基线

先把用户流程、证据引用和安全边界固定下来，才能判断 Embedding 或 LLM 是否真正带来提升。否则只能展示“模型生成了一段话”，无法证明答案更准、更可追溯或更适合售前使用。

### 如何控制幻觉和错误承诺

1. 回复只能由检索到的资料句子组成。
2. 识别“没有承诺”“需要人工确认”“不得自行推断”等阻断语句。
3. 阻断场景不展示通用产品介绍作为匹配能力。
4. 对价格、部署、安全等问题生成继续询问清单。
5. 报告底部提醒售前或产品负责人复核。

## 可验证结果

- 自动化测试：26 项全部通过（包含作品集文档一致性检查）。
- 冻结开发评测：10/10 通过，Top-3 来源命中率、Top-1 来源准确率、关键风险题通过率均为 100%。
- 本地规则评测不产生 API 费用；单次评测的延迟会随电脑负载变化，不作为生产 SLA。

## 下一步演进

1. 收集至少 3 名真实售前/产品用户的任务反馈，补充到 `docs/user-research.md`。
2. 在同一冻结题集上比较 TF-IDF、Embedding 和混合检索。
3. 如确有收益，再接入大模型做结构化草稿，并保留来源、拒答和成本门槛。
4. 需要多人使用时，再设计登录、权限、云端数据库和敏感资料隔离。
