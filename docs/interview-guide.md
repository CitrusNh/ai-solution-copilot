# 面试讲解材料

## 1. 为什么选售前，而不是普通聊天机器人？

售前有明确业务结果：快速找到价格、部署和安全证据，减少错误承诺，让回复可以复核和交接。这个场景同时体现产品设计、检索、风险控制和商业沟通，比只生成一段文字更容易验证价值。

## 2. 为什么先做本地规则基线，再接聊天模型？

如果第一版直接接模型，很难判断提升来自检索、提示词还是语言表达。我先冻结 10 道题和风险门槛，建立零 API 成本的确定性基线；之后聊天模型只负责增强分析和表达，程序继续控制证据引用、输出结构和人工确认边界。

## 3. 整体 RAG 流程是什么？

资料经过解析、OCR 和切分后保留来源元数据；客户问题通过 TF-IDF 与业务意图加权检索 Top-3；规则层先生成可解释结论；可选聊天模型接收问题、内部证据和公开搜索摘要，输出固定 JSON；服务端校验后展示并写入报告。

## 4. 为什么不用 Embedding 作为当前默认检索？

演示资料规模小，字符级 TF-IDF 成本为零、结果稳定且容易解释。项目已经准备 Embedding 与混合检索实验，但是否替换必须在同一评测集上比较质量、延迟和费用，不能因为“用了向量”就认为产品更好。

## 5. 如何控制幻觉和错误承诺？

- 内部证据 `D` 是产品能力唯一依据，公开资料 `W` 只补充背景。
- 对 BYOK、等保、数据驻留等未知安全需求设置确定性阻断。
- 模型输出必须符合固定 JSON，并引用存在的证据编号。
- 资料不足时，回复必须包含不能承诺或人工确认语言。
- 检索材料被视为不可信文本，提示模型忽略其中夹带的指令。
- 模型超时、限流、格式错误或引用越界时自动降级到本地规则结果。

## 6. 扫描 PDF OCR 怎么实现？

先用 `pypdf` 读取每页文本层，字符过少时用 PyMuPDF 以 2 倍比例渲染，再交给 RapidOCR 本地识别。输出保留 `第 N 页 · OCR`。单文件最多处理 20 个扫描页，控制公共 Demo 的资源消耗。

## 7. 联网搜索如何处理隐私和可信度？

联网默认关闭，开启后只发送客户问题，不上传企业文档。结果过滤无效和重复 URL，显示标题、摘要和链接，并与内部资料分开。搜索异常不会中断本地分析，互联网资料不能用于证明本产品能力。

## 8. 聊天模型现在是否真实上线？

代码、结构化输出、引用校验、人工确认门槛、失败降级和模拟兼容 API 测试已完成。当前 APINebula Key 只开放图片模型，没有聊天权限，所以公网真实聊天调用尚未开启。更换有聊天权限的 Key 并配置 `CHAT_MODEL` 后，页面开关会启用。

## 9. 如何评估系统？

冻结 10 道开发题，检查 Top-3 来源、Top-1、置信状态、事实和关键风险术语；BYOK、等保、数据驻留三题必须全部通过。当前开发集 10/10、关键风险 3/3，33 项自动化测试通过。真实联网和扫描 PDF OCR 冒烟通过，但真实用户反馈仍待收集。

## 10. 项目有哪些不足？

不是生产级企业系统：没有登录、权限、多租户、审计和云端持久化；开发评测集小；公开搜索依赖外部网络；OCR 对模糊、旋转或复杂表格扫描件可能失败；当前聊天 Key 无权限；还没有真实目标用户数据。

## 11. 下一步如何验证商业价值？

找至少 3 名售前、解决方案或产品人员完成同一组任务，记录完成时间、检索是否正确、回复人工修改率、有用性评分和错误承诺情况。再让规则版与聊天增强版 A/B 对比，同时记录 Token、延迟和成本。

## 12. 你个人体现了什么能力？

我从用户痛点和 PRD 出发，把资料解析、检索、风险决策、AI 接口、评测、部署和作品集材料连成一个可运行闭环。重点不是堆技术，而是为每项能力定义业务作用、失败边界和验证方式。
